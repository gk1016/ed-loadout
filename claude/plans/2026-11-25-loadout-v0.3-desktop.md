# LOADOUT v0.3 — a windowed app, not a console

Graham, 2026-11-25 13:23 CT: "we are not doing command line stuff with our products." Double-clicking `LOADOUT_Portable.exe` on the laptop opened a console that closed at once. v0.3 makes LOADOUT a Qt desktop app in the FRAGO/S-4 grammar with a `LOADOUT_Setup.exe` installer. The CLI survives as the engine underneath and for scripting; it is no longer what a user sees.

## Goal
A commander installs `LOADOUT_Setup.exe`, opens LOADOUT, sees what the machine is and what will be applied, presses APPLY, and is done; every write is shown and backed up.

## Non-goals
No new detection or tier logic (v0.2 as is, plus the two v0.2.1 fixes folded in below). No self-update yet. No ED-UP ini. No cloud sync of profiles. No change to the CLI's flags.

## Layout (one window, desk 1100+ px; flight posture not required in v0.3)
```
command bar 30px : LOADOUT mark | MACHINE <hostname> | GPU <name> | PANEL <w>x<h>@<hz> | TIER T1 | v0.3.0
tool rail 40px   : HOME / PROFILES / LOG / SETTINGS
SplitView
  left  : PROFILES pane - rows: name, source machine, captured, files; CAPTURE THIS MACHINE / IMPORT FOLDER buttons in a ruled bar
  right : HOME pane - two ruled sections:
          DETECTED  (facts as label/value rows, controllers as GUID chips, missing bound devices in red)
          WILL APPLY (one row per derived/overridden key: key, value, source, reason; file targets listed)
          action bar: DETECT AGAIN | APPLY <profile> | RESTORE LAST BACKUP
status bar 24px  : Options dir | last backup stamp | game running? (red when EliteDangerous64.exe is up) | build sha
```
APPLY opens a modal confirm listing every file to be written and the backup folder; disabled while the game runs. The LOG rail page shows the same lines the CLI prints. SETTINGS: profiles folder (default `%LOCALAPPDATA%\LOADOUT\profiles`), Options dir override, theme deepfield/daylight.

## Acceptance criteria
1. **Repo shape**: crate moved to `rust/` as `loadout-core` (`crate-type = ["staticlib","rlib"]`, cxx), the CLI kept as `rust/src/bin/ed-loadout.rs` over the same library; every existing test passes unchanged from `rust/` (`cargo test` there: 40 + 14). The v0.2.1 fixes land here: (a) GPU names containing `Laptop` other than `RTX 5090 Laptop` / `RTX 5080 Laptop` -> T3; (b) `max_fps` = the largest divisor of the panel refresh <= 144 (240->120, 165->165, 144->144, 360->120, 120->120), reason text updated; unit tests for both; version `0.3.0`.
2. **Bridge**: `rust/src/bridge.rs` (`#[cxx::bridge]`) exposes `detect() -> String` (JSON of Facts + derived rows), `list_profiles(dir) -> String`, `capture(options, out, machine) -> String`, `plan_apply(profile, options, machine) -> String` (the files and edits that WOULD happen, no writes), `apply(profile, options, machine) -> String` (result + backup path), `restore(options, backup) -> String`, `game_running() -> bool`. No panic can cross: every fn returns a JSON `{ok, error, ...}`; `unwrap`/`expect` lints as in FRAGO.
3. **Qt shell**: `CMakeLists.txt`, `cpp/main.cpp` (+ `cpp/core.h/.cpp` QObject wrapper exposing the bridge to QML with `Q_INVOKABLE`s and signals), `qml/Main.qml`, `qml/Theme.qml` (FRAGO's, tokens unchanged), `qml/Btn.qml`, `qml/Kicker.qml`, `qml/Rail.qml`, `qml/HomePage.qml`, `qml/ProfilesPage.qml`, `qml/LogPage.qml`, `qml/SettingsPage.qml`, `qml/ConfirmApply.qml`, `fonts/` (the three families, copied from FRAGO), `icons/loadout.ico` + an SVG mark (an original mark: a bracketed hexagon with a horizontal rule; no third-party art). Layout per the diagram; the design rules above are acceptance, checked on the survey shots.
4. **Scripts**: `build.ps1`, `package.ps1`, `ship.ps1 -NoRelease`, `shots.ps1 -Survey <tag>` and `loadout.iss` (`AppName=LOADOUT`, `{localappdata}\LOADOUT`, `OutputBaseFilename=LOADOUT_Setup`) adapted from FRAGO with names changed and the engine/Drive parts removed (LOADOUT has no engine, no Drive copy). `ship.ps1 -NoRelease` ends `=== VERIFY OK (no release) ===`; `shots.ps1 -Survey <tag>` writes `_shots\uipass\survey-<tag>\index.md` + jpgs for `home`, `profiles`, `log`, `settings`, `confirm` in deepfield and daylight at 1320 wide, log ends `=== SURVEY OK ===`.
5. **Behaviour on the box** (survey + a scripted run): opening the exe with no profile folder shows HOME with DETECTED filled and WILL APPLY saying no profile yet; CAPTURE THIS MACHINE creates `%LOCALAPPDATA%\LOADOUT\profiles\<hostname>` and it appears in PROFILES; selecting a profile fills WILL APPLY with the merged rows (derived + `[machine.*]` sources); APPLY shows the confirm with the file list and backup path, writes, and the LOG page shows the lines; RESTORE LAST BACKUP puts the files back byte-identical (test via the CLI `diff`). Game-running state disables APPLY and shows red in the status bar (test by injecting `running=true` through a `LOADOUT_FAKE_GAME_RUNNING=1` env read only in debug builds).
6. **Installer**: `package.ps1` produces `..\transfer\LOADOUT_Setup.exe`; installing it on a clean user profile puts `loadout.exe` under `%LOCALAPPDATA%\LOADOUT`, a Start-menu entry, and double-clicking opens the window (no console). Evidence: the installer size and a shot of the installed app's HOME.
7. **README** rewritten for the app (install, what the screen shows, where backups go, that the CLI still exists for scripting); `ISSUES.md` updated; `.github/workflows/release.yml` adjusted by Cowork after merge (not Code) to run on the Windows runner and attach `LOADOUT_Setup.exe`.
